## When to use ohmyho.st

Use ohmyho.st when the customer wants to develop or deploy an app using its managed versions or selected GitHub source; inspect a project's deployment, database or DNS/mail readiness; manage usage and budgets; or request an encrypted SQL export. Use the transport and operations available in this client.

Your agent follows the [get-started Skill](https://ohmyho.st/skills/ohmyhost-get-started/SKILL.md) for installation, sign-in and workspace selection before its first deployment ([what it covers](/skills#start-with-the-get-started-skill)).

Ask which account is signed in to read its current email and scoped workspace IDs and names through `identity_get`, on either transport. A user API token identifies its owner; machine-to-machine credentials have a null email. [Current account details](/login-tokens#check-the-current-account).

Start with `identity_get`, then select the customer's project with the available list tool: remote `project_list` or local `projects_list`. Read `project_context_get` and `source_get` before acting. Use `include_binding: true` on `source_get` before using connection/generation guards. Default GitHub reads preserve their existing status fields; managed reads always include the full binding. The server's current source binding is authoritative; an agent's location or copied Git remote does not replace it. A new app developed entirely in chat starts with managed versions, while an explicitly selected GitHub repository uses GitHub. Configure only the capabilities the application needs and keep its chosen authentication provider. Use the matching [task Skill](/skills) for the workflow.

For a new project, ask whether Dev should be protected or public before `project_create`; protected is the default. `project_dev_share_link_get` returns the Owner's reusable protected link. Local clients expose `project_dev_access_mode_set` to change the choice, while `project_dev_share_link_rotate` and `project_dev_share_link_revoke` block old links and browser sessions on their next request. Discover the connected client's actual tools before requesting those changes. [Dev access details](/environments#choose-who-can-open-dev).

When the client's tools support the requested custom domain before the first Prod deployment, use `domain_paid_plan` and `domain_paid_apply` to reserve it, then `domain_cloudflare_authorize` and `domain_cloudflare_status` for scoped consent. `awaiting_deployment` means no DNS or certificate provisioning has started. Deploy and verify the Prod hosting address, then repeat `domain_paid_apply` with the original hostname and idempotency key. Consent and deployment alone do not activate it. [Domain setup](/domains).

## Connected chat with remote OAuth

For a client that supports authenticated remote MCP, connect:

```text
https://app.ohmyho.st/mcp
```

Complete the client's OAuth sign-in. The agent verifies `identity_get`, the intended workspace and the requested project before continuing. Current workspace membership, role and any explicit token restrictions determine access. If you already described an application or task, the agent continues it; otherwise it asks what you would like to host.

Existing authenticated connections continue to use their current OAuth identity. If a client has cached older tools or instructions, refresh its catalog or start a fresh chat; a catalog refresh does not require a new OAuth connection. A role or resource denial needs the appropriate current access. An account with no workspace can use `workspace_setup` and verify identity again afterward.

The client manages its OAuth credential; there is no copied platform token or local device-code login in a connected chat. Verify an authenticated tool call and discover this server's actual tools. A private application value uses a one-hour [secret link](/secrets#set-a-secret-from-a-connected-chat) that needs no sign-in. GitHub setup and Native Auth provider secrets use protected portal links that last ten minutes and need a portal sign-in as the same user who connected the chat. `connection_status` reports the status of each link. [Runtime secrets](/secrets) describes secret input.

For a complete file tree, the remote tools are `source_upload_prepare`, `source_blob_put`, `source_upload`, `source_upload_commit` and `source_switch`. They use actual file contents available to the client; a local directory path gives the chat no filesystem access. Blob uploads return server-computed hash/length receipts. Retain those exact receipts for the complete manifest, and require a succeeded operation plus a committed upload before using its saved SHA. Saving or switching source starts no deployment. Follow [the full snapshot and switch flow](/sources#save-a-complete-tree-in-chat).

MCP file reads return valid UTF-8 as `content_text` by default, or base64 when the file cannot be decoded. Remote `source_files` accepts `path` and `format: "text" | "base64"`; local `source_file` provides the corresponding file read. `source_changes` accepts exactly one `content_text` or `content_base64` per change, with null base64 for deletion. Follow the returned schemas and preserve the file's executable flag and source revision guards.

## Install and sign in locally

<InstallClients />

The local stdio MCP server uses `OHMYHOST_TOKEN` when that variable is set in the server process, and otherwise the logins saved by ohmyhost login. With several, pass `profile_name` per call (`profile_list` shows names) or bind the server to `OHMYHOST_PROFILE`=NAME; another requested profile fails `profile_context_mismatch`. A login added later works on the next call without restarting. A token on its own is enough — no login and no browser. Put it in the same `env` block as `OHMYHOST_ENVIRONMENT`; the server reads no `.env` file and never calls the CLI.

With a token, every tool works except `organization_create`, `organization_list`, `organization_use`, `token_create`, `tokens_list` and `token_revoke`. Those need an interactive login: run the matching `ohmyhost` command in a shell without `OHMYHOST_TOKEN`.

After installing or upgrading the clients, restart the MCP server. A running server keeps the tool list it started with, so newly published tools stay invisible until it restarts.

Keep existing servers, models and permission settings. If a server named `ohmyho` is already configured, inspect it before changing that entry. An old npx configuration pinning a versioned release URL stops when that archive is superseded; use the installed ohmyhost-mcp command. Preserve harness approval policy; rejected mutations are not platform failures, and switching transport cannot bypass approval.

The server's source is published with every release at [amerged-org/ohmyhost-mcp](https://github.com/amerged-org/ohmyhost-mcp), every file of @amerged/ohmyhost-mcp except its built dist bundle and README, byte for byte. release.json records full-package npm integrity and the SHA-256 of omitted files. For help, ask your agent: it reports through `feedback_submit` and follows up with `feedback_status` ([Support](/support)).

## Codex

```sh
codex mcp add ohmyho --env OHMYHOST_ENVIRONMENT=production -- ohmyhost-mcp
```

Reload the connection if requested, then ask Codex to call `identity_get` and list the available Skills.

## Claude Code

```sh
claude mcp add --transport stdio --scope user --env OHMYHOST_ENVIRONMENT=production ohmyho -- ohmyhost-mcp
```

Open `/mcp` in Claude Code and confirm the connection. Ask it to call `identity_get`.

## Cursor

Merge this server into your existing `~/.cursor/mcp.json`, or `.cursor/mcp.json` for this project:

```json
{
  "mcpServers": {
    "ohmyho": {
      "command": "ohmyhost-mcp",
      "env": { "OHMYHOST_ENVIRONMENT": "production" }
    }
  }
}
```

[Download this configuration](https://ohmyho.st/mcp.json). It contains no token. Check the MCP connection in Cursor settings; current Cursor CLI also supports `agent mcp list-tools ohmyho`. Use your installed CLI's help if its executable is named differently.

## Hermes

```sh
hermes mcp add ohmyho --command ohmyhost-mcp --env OHMYHOST_ENVIRONMENT=production
hermes mcp test ohmyho
```

Start or reload the agent session after changing settings. Preserve your installed Hermes version and model unless the reported missing capability requires an update.

## OpenClaw

For versions with the native outbound MCP registry:

```sh
openclaw mcp add ohmyho --command ohmyhost-mcp --env OHMYHOST_ENVIRONMENT=production
openclaw mcp probe ohmyho --json
```

Use the installed `openclaw mcp add --help` to confirm support. `mcp serve` exposes OpenClaw itself and is a different feature. Preserve the current approval policy; a saved registry entry alone does not prove that the running agent has loaded it.

## Confirm the connection

Ask the agent: “Read my ohmyho.st identity and list my projects.” It should call `identity_get`, then remote `project_list` or local `projects_list`, and read `project_context_get` for the project you select. If a tool is missing, compare the installed client with the [current release](https://ohmyho.st/client-release.json) and reconnect after updating.

These harness commands and the downloadable MCP configuration set up the local `ohmyhost-mcp` stdio server, with its CLI/device-login profiles and private automation-token support. Its published catalog describes that local client. The remote product endpoint above is a separate OAuth connection. Keep the transport your client supports and its existing permission policy. Mintlify's search MCP answers documentation questions; it cannot deploy or access your account.
