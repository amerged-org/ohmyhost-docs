# Build an app for ohmyho.st

Prepare the application's real capabilities, then verify them after deployment.

## Choose a framework for a new app

Keep the customer's chosen stack and authentication. When there is no existing framework:

- For a protected form with a customer login, PostgreSQL and an admin view, use **Next.js App Router with TypeScript**. In a native chat, choose managed source with the `empty` template. Start from a real, accessible `package.json` and its matching frozen lockfile at one immutable revision. Save the actual bytes and verify their sizes and SHA-256 values in the persisted source. The [pinned Next.js reference and Native Auth bindings](references/stack-contracts.md#form-and-admin-apps) give a working starting point.
- For a small React form, use **Vite and TypeScript**. The `vite-react` template supplies the frontend. Render the real form at `/`. When it needs server data, use the same-origin `/api/*` routes in `src/ohmyhost/companion.ts` and select edge mode. Submit controls to those routes and verify the root in a browser.
- For lightweight HTTP handlers, server-rendered HTML or a scheduled job, use a **plain TypeScript Worker**. Select `runtime.mode: functions`, export `fetch` from `src/ohmyhost/worker.ts`, and export a `scheduled` handler on the same default object when the app uses a cron. Enable the capabilities that the chosen flow actually uses.

Verify the user's requested action in the hosted browser. Submit a record and read it back after a reload. For protected data, check a guest, a signed-in customer and an authorized admin against the same record, then sign out and check access again. For a Live Preview, save a visible source edit and observe it in the same open tab at the same URL. For a scheduled outcome, observe an actual UTC invocation and its persisted effect.

Use `preview_open` to get the project's private live preview on Free or Paid. Pass `environment: dev` if the workspace is Paid and the project has Dev. Otherwise pass `environment: prod`. Those arguments select the preview's environment. Accepted source saves update the preview without deploying. A preview link works for at most 24 hours; `preview_open` then creates a new preview with a new link. Use `preview_get`, `preview_stop`, and `preview_rotate` to inspect, stop, or replace that URL, and keep it private. When a result carries `failure`, follow its `next_step` instead of waiting. For a Native Auth preview, rollout approval is checked before Paid coverage. For `native_auth_launch_unavailable`, ask ohmyho.st support to check rollout access for the workspace and project. For `paid_plan_required` during Native Auth preparation, ask the owner to check the workspace plan. Wake the same preview after the reported requirement is satisfied.

1. Inspect the selected repository and, with a local checkout, run `ohmyhost init --dry-run --json`. In a native chat, inspect the saved source files and apply the runtime references through the remote file tools; use the actual plan/build diagnostics, without claiming a local command ran. Preserve a valid existing `ohmyhost.yaml`, application root, egress rules, auth choice and migrations. Resolve the returned blockers and requirements rather than replacing the configuration with a reduced file.
2. Keep one exactly pinned package manager and its matching lockfile. Read `compatibility.frameworks[].status`: `admitted` meets the framework's security floor, `pending` is a version range the build checks after installing it, and `unsupported` blocks until the package is at its `minimum` or a later stable release.
3. Read [the runtime contracts](references/stack-contracts.md) for the capabilities the app needs. Keep ordinary Astro pages/endpoints, Next.js routes, native TanStack Start server functions, the returned Vite API companion contract, or a plain Worker module (`runtime.mode: functions`, `src/ohmyhost/worker.ts`). The service supplies its build adapter; do not add customer Wrangler/OpenNext configuration merely to host the app. Next.js 16 Cache Components and `"use cache"` build here: request-time `"use cache"` values are never stored, prerendered values stay until the next deployment, and revalidation is refused by default. An app that requires `revalidatePath` can explicitly opt into the bounded writable-cache mode described in the contracts; explain its response buffering and supported request contexts first. A `create-next-app` 16.4 app with Tailwind CSS first needs the PostCSS configuration the contracts describe (`next_tailwind_turbopack_only`). Video, audio or microphone need the `_headers` opt-in from the contracts.
4. For managed Postgres, use the supported application database binding and immutable expand-only migrations. Name every migration file `YYYYMMDDHHMMSS_name.sql`: fourteen digits, an underscore, then lowercase letters, digits, `_` or `-`, for example `20261123093000_create_inquiries.sql`. A name such as `0001_inquiries.sql` is refused and the preview does not start. Never edit a migration that was applied; add a new file. Reach it through `createPrivateDatabaseClient`; use bounded `withConnection` for interactive transactions. Keep network transfers, email and AI calls outside that connection scope. Adding nullable columns without defaults is admitted; DROP, row changes, CREATE OR REPLACE and other changes to existing schema are refused. Preserve production records and read the database Skill for migration limits, sizing, data assignments or reset.
5. Preserve the customer's authentication choice. Better Auth and customer-owned WorkOS are the verified integrations; any other OAuth or OIDC provider has its own setup and runtime requirements and no completed support claim. Omh Native Auth is available on projects approved for the Native Auth launch. Choose it explicitly and verify the project's readiness and hosted login. For Google or GitHub sign-in, the project Owner supplies a customer-owned OAuth application for each selected environment. Follow the runtime reference and verify the exact callback and a real sign-in before reporting support for that project. Configure actual callback/logout URLs and server secrets, then test login, a protected route, reload and logout. A public app needs no auth provider. Detect actual Supabase capability usage before proposing a migration; an SDK declaration alone does not justify replacing it.
6. For sending or receiving email, follow [the mail workflow](references/mail.md): choose the customer domain explicitly, prepare and verify a signed application webhook before receiving, and store incoming mail in the customer database. Mail and files use `(request) => fetch(request)` to the injected `*_GATEWAY_URL` values; their origins are allowed automatically and never go in `runtime.egress.allow`. Database access keeps its `OHMYHOST_DATABASE` service binding. Enable only used capabilities. Other server requests to an origin omitted from `runtime.egress.allow` answer HTTP 403 `Egress denied`; browser resources use the separate declared `runtime.browser` policy. Use the current client/runtime libraries and let `init` report missing routes or capabilities. Do not remove a required feature just to obtain a successful build.
7. For LLMs, images, speech, classifiers or OCR, follow [the AI gateway workflow](references/ai.md): declare `ai.enabled` and a jurisdiction the customer chose, select a compatible orq.ai model from the injected endpoint's `/models`, call it from server code only, and handle credit and gateway failures. Realtime voice has a server-side WebSocket route that passed a real hosted session; keep the socket in server code and close it yourself, because a session ends after five minutes at most.
8. For server-side HTML/CSS-to-PDF, use the [Browser PDF workflow](references/browser-pdf.md). It is one managed service usable from both customer Dev and Prod. Keep its injected key server-only, use embedded assets, and enforce the application's own access rules.
9. Run the application's relevant tests, typecheck and framework build through the available execution tools. Prefer focused regressions for the changed behavior and real hosted capability checks; respect the customer's requested verification scope without adding a broad test program. A native chat without test execution must identify that limitation and use actual hosted plan/build results and interaction checks, not invent test success. Use **ohmyhost-deploy** to reuse the saved source, deliver environment secrets privately and verify the hosted app's required reads, writes and integrations.

Resolve hosted bindings and trusted configuration from the framework's actual request context. A localhost-only test runtime or a successful health endpoint does not establish production login, tenant setup or background processing. Follow the runtime reference for first-user bootstrap, private uploads and bounded scheduled work when the application needs them.

See [amerged-org/ohmyhost](https://github.com/amerged-org/ohmyhost) for the ohmyho.st hosting platform (OMH) and [amerged-org/cloudflare-postgres](https://github.com/amerged-org/cloudflare-postgres) for its PostgreSQL infrastructure (PGCF).

For first account setup, use **ohmyhost-get-started**. For publishing, use **ohmyhost-deploy**;
use **ohmyhost-deploy-github** only for the selected GitHub source route. [The CLI reference](references/cli-deploy.md) supplies detailed commands when a local checkout is available. For a failed operation, use **ohmyhost-troubleshoot-deployment** and retain its original ID.

Report a suspected hosting bug with `feedback_submit` and a minimal redacted reproduction. Return a working application URL only after its required flows pass. Promotion, rollback and deletion follow the customer's requested scope; an ordinary deploy does not require deleting their app for a cleanup test.

## Astro

Use the [Astro guide](https://docs.ohmyho.st/frameworks/astro). Static uses `astro build`, `runtime.mode: static` and `build.output: dist` without a server adapter. SSR uses the official `@astrojs/cloudflare` adapter, `output: "server"`, `runtime.mode: edge`, `build.output: dist/client`, `session: false` and `cloudflare({ imageService: "passthrough" })`. Keep the standard `src/` and output directories. The service supplies the deployment config. No native KV sessions, provider cache, Images or customer-defined Cloudflare resources are supported initially. Keep server imports in frontmatter or ordinary modules; put dynamic browser imports in a normal statically imported browser module rather than an Astro template. Verify request-time behavior plus browser islands under hosted CSP. Static build-time filesystem/MDX work remains ordinary Node build work; enable no request-time capabilities on a static plan.
