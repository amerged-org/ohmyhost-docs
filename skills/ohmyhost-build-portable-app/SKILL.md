# Build an app for ohmyho.st

Use the [customer voice](../ohmyhost-get-started/references/customer-voice.md) in replies.

Anyone can read the [ohmyho.st platform source](https://github.com/amerged-org/ohmyhost) to trace a build or deployment, and the [managed PostgreSQL source](https://github.com/amerged-org/cloudflare-postgres) to trace a database change. Your app’s code stays in your project.

## Hard runtime budgets & pre-save checklist

- **Worker request budget**: 50 ms CPU and 10 subrequests per request; 120 s wall clock for scheduled runs; no headless browser or heavy native binary inside the request Worker (use [Browser PDF](references/browser-pdf.md) or [container jobs](references/container-jobs.md)).
- **Next.js bundle budget**: at most 25 MiB per Worker module, 10 MiB gzipped Worker bundle, and 64 MiB source map (prefer plain Route Handlers over many duplicated Server Actions, and keep `lucide-react`/chart/PDF packages lean).
- **Pre-save checklist**: keep `database.migrations` in `ohmyhost.yaml` when the app uses PostgreSQL; keep `@ohmyhost/customer-runtime` in `package.json`; name every migration `YYYYMMDDHHMMSS_name.sql` (never `0001_...`); route app-owned Better Auth password hashing through the platform password-hashing binding rather than pure-JS `scrypt` in the Worker; check `ohmyhost init --dry-run --json` locally before saving.

Prepare the application's real capabilities, then verify them after deployment.

For a finite task that needs its own npm, Python or native binary dependencies, publish a private job from the project Dockerfile. The job entry point receives private files, produces an output manifest and stops. Use the [container job workflow](references/container-jobs.md) for version, credit and cancellation details.

## Choose a framework for a new app

Keep the customer's existing framework and sign-in. For a new app in chat, use the
[Vite template and API companion](references/chat-stack.md), including for data or sign-in.
For a specifically chosen framework, follow its configuration in the runtime references.
For lightweight HTTP handlers, server-rendered HTML or a scheduled job, use a
plain TypeScript Worker (`runtime.mode: functions`, `src/ohmyhost/worker.ts`, default
`fetch` and, for cron, `scheduled` on the same object). For Next.js, use the
[pinned local or GitHub reference](references/stack-contracts.md#form-and-admin-apps).

Verify the user's requested action in the hosted browser. Submit a record and read it back after a reload. For protected data, check a guest, a signed-in customer and an authorized admin against the same record, then sign out and check access again. For a preview, save a visible source edit and observe it in the same open tab at the same URL. For a scheduled outcome, observe an actual UTC invocation and its persisted effect.

Show the saved app using the [preview workflow](../ohmyhost-deploy/references/preview.md).
For a blocked Native Auth preview, use the [troubleshooting workflow](../ohmyhost-troubleshoot-deployment/SKILL.md).

1. Inspect the selected repository and, with a local checkout, run `ohmyhost init --dry-run --json`. In a native chat, inspect the saved source files and apply the runtime references through the remote file tools; use the actual plan/build diagnostics, without claiming a local command ran. Preserve a valid existing `ohmyhost.yaml`, application root, egress rules, auth choice and migrations. Resolve the returned blockers and requirements rather than replacing the configuration with a reduced file.
2. Keep one pinned package manager and its lockfile. For additions to the managed pnpm starter in chat, edit `package.json`.
   Follow the [chat dependency workflow](references/chat-stack.md). Read `compatibility.frameworks[].status`: `admitted` meets the framework's security floor, `pending` is a version range the build checks after installing it, and `unsupported` blocks until the package is at its `minimum` or a later stable release.
3. Read [the runtime contracts](references/stack-contracts.md) for the capabilities the app needs. Keep ordinary Astro pages/endpoints, Next.js routes, native TanStack Start server functions, the returned Vite API companion contract, or a plain Worker module (`runtime.mode: functions`, `src/ohmyhost/worker.ts`). The service supplies its build adapter; do not add customer Wrangler/OpenNext configuration merely to host the app. Next.js 16 Cache Components and `"use cache"` build here: request-time `"use cache"` values are never stored, prerendered values stay until the next deployment, and revalidation is refused by default. An app that requires `revalidatePath` can explicitly opt into the bounded writable-cache mode described in the contracts; explain its response buffering and supported request contexts first. A `create-next-app` 16.4 app with Tailwind CSS first needs the PostCSS configuration the contracts describe (`next_tailwind_turbopack_only`). Video, audio or microphone need the `_headers` opt-in from the contracts.
4. For managed Postgres, use the supported application database binding and immutable expand-only migrations. Name every migration file `YYYYMMDDHHMMSS_name.sql`: fourteen digits, an underscore, then lowercase letters, digits, `_` or `-`, for example `20261123093000_create_inquiries.sql`. A name such as `0001_inquiries.sql` is refused and the preview does not start. Never edit a migration that was applied; add a new file. Reach it through `createPrivateDatabaseClient`; use bounded `withConnection` for interactive transactions. Keep network transfers, email and AI calls outside that connection scope. Adding nullable columns without defaults and bounded replacements of functions or triggers created by an earlier applied migration are admitted. Add a later file, review its replacement targets in the exact saved commit plan or isolated Prod promotion plan and keep the function declaration unchanged outside its body. Follow the [database migration rules](../ohmyhost-manage-database/SKILL.md#schema-and-promotion) for eligible triggers, preserved properties and recovery. The preview does not create the database by itself: when `preview_open` reports `data.state` `needs_database` or `migrations_pending`, ask the user where to apply the migration files and call `database_migrate` as the ohmyhost-deploy Skill describes. Preserve production records and read the database Skill for migration limits, sizing, data assignments or reset.
5. Recommend **ohmyho.st Native Auth** first for a new application that needs login. Check launch approval, Paid coverage, the verified sender and canonical origin before selecting `auth.provider: omh-native`. Native Auth hashes passwords in a platform Worker. Preserve an existing authentication provider unless the customer chooses to switch. For app-owned Better Auth email/password on a deployed Worker with managed PostgreSQL, wire both callbacks through [the private password hashing binding](references/stack-contracts.md#app-owned-password-hashing). Customer-owned WorkOS AuthKit also keeps password handling outside the app Worker. For Google or GitHub sign-in with Native Auth, use the owner's OAuth application for each selected environment. Verify a real sign-in, a protected route, reload and logout. A public app needs no auth provider. Detect actual Supabase usage before proposing a migration.
6. For sending or receiving email, follow [the mail workflow](references/mail.md): choose the customer domain explicitly, prepare and verify a signed application webhook before receiving, and store incoming mail in the customer database. Mail and files use `(request) => fetch(request, { redirect: "manual" })` to the injected `*_GATEWAY_URL` values; their origins are allowed automatically and never go in `runtime.egress.allow`. Database access keeps its `OHMYHOST_DATABASE` service binding. Enable only used capabilities. Other server requests to an origin omitted from `runtime.egress.allow` answer HTTP 403 `Egress denied`; browser resources use the separate declared `runtime.browser` policy. Use the current client/runtime libraries and let `init` report missing routes or capabilities. Do not remove a required feature just to obtain a successful build.
7. For LLMs, images, speech, classifiers or OCR, follow [the AI gateway workflow](references/ai.md): declare `ai.enabled` and a jurisdiction the customer chose, select a compatible orq.ai model from the injected endpoint's `/models`, call it from server code only, and handle credit and gateway failures. Realtime voice has a server-side WebSocket route that passed a real hosted session; keep the socket in server code and close it yourself, because a session ends after five minutes at most.
8. For server-side HTML/CSS-to-PDF, use the [Browser PDF workflow](references/browser-pdf.md). It is one managed service usable from both customer Dev and Prod. Keep its injected key server-only, use embedded assets, and enforce the application's own access rules.
9. Run the application's relevant tests, typecheck and framework build through the available execution tools. Prefer focused regressions for the changed behavior and real hosted capability checks; respect the customer's requested verification scope without adding a broad test program. A native chat without test execution must identify that limitation and use actual hosted plan/build results and interaction checks, not invent test success. Use **ohmyhost-deploy** to reuse the saved source, deliver environment secrets privately and verify the hosted app's required reads, writes and integrations.

Resolve hosted bindings and trusted configuration from the framework's actual request context. A localhost-only test runtime or a successful health endpoint does not establish production login, tenant setup or background processing. Follow the runtime reference for first-user bootstrap, private uploads and bounded scheduled work when the application needs them.

When a guide is unavailable or a plan names a file or rule, use the [source pointers](references/source-pointers.md)
to look up the current contract.

For first account setup, use **ohmyhost-get-started**. For publishing, use **ohmyhost-deploy**;
use **ohmyhost-deploy-github** only for the selected GitHub source route. [The CLI reference](references/cli-deploy.md) supplies detailed commands when a local checkout is available. For a failed operation, use **ohmyhost-troubleshoot-deployment** and retain its original ID.

Report a suspected hosting bug with `feedback_submit` and a minimal redacted reproduction. Return a working application URL only after its required flows pass. Promotion, rollback and deletion follow the customer's requested scope; an ordinary deploy does not require deleting their app for a cleanup test.

## Astro

Use the [Astro guide](https://docs.ohmyho.st/frameworks/astro). Static uses `astro build`, `runtime.mode: static` and `build.output: dist` without a server adapter. SSR uses the official `@astrojs/cloudflare` adapter, `output: "server"`, `runtime.mode: edge`, `build.output: dist/client`, `session: false` and `cloudflare({ imageService: "passthrough" })`. Keep the standard `src/` and output directories. The service supplies the deployment config. No native KV sessions, provider cache, Images or customer-defined Cloudflare resources are supported initially. Keep server imports in frontmatter or ordinary modules; put dynamic browser imports in a normal statically imported browser module rather than an Astro template. Verify request-time behavior plus browser islands under hosted CSP. Static build-time filesystem/MDX work remains ordinary Node build work; enable no request-time capabilities on a static plan.
